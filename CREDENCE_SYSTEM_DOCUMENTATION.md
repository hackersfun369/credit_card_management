# Credence — Credit Card Management System

> **Implementation reference** — generated from the current Angular application and Spring Boot microservice source.  
> Frontend: `credIT-angular` (`http://localhost:4200`) · Customer: `8081` · Cards: `8082` · Transactions: `8083` · Merchant: `8084` · Manager/Auth: `8085`.

## 1. Purpose

Credence is an operations console for managing customers, credit-card accounts, merchants, transactions, repayments, renewals, due dates, and card-risk alerts. It uses live API data; the frontend does not maintain a hard-coded data set.

The central account model is important:

- One customer can have at most **two current physical cards**: one `PRIMARY` and one `ADD_ON`.
- A primary/add-on pair belongs to one shared card account. Both use the same tier, credit limit, available credit, due date, and expiry date.
- A renewal creates replacement physical cards and preserves the balance/account context. Historic cards remain in the database for auditability but are no longer treated as current.

## 2. Architecture

```text
Angular UI (4200)
  ├─ Manager/Auth API (8085): manager registration, login, JWT refresh
  ├─ Customer API (8081): customer lifecycle
  ├─ Credit Card API (8082): cards, balances, statuses, renewal, billing dates
  ├─ Transaction API (8083): purchases, payments, statuses, credit reservations
  └─ Merchant API (8084): merchant lifecycle and transaction eligibility

Database: Oracle (each service uses its JPA entity/repository)
Service-to-service calls:
  Customer → Card service (deactivate customer cards before deletion)
  Transaction → Card service (reserve/release/replenish shared available credit)
```

### Runtime data flow

1. A manager signs in at the Angular login page.
2. Manager service returns a signed JWT, expiry time, username, and role.
3. The Angular session stores the token and attaches `Authorization: Bearer <token>` to API calls.
4. Angular loads customers, cards, merchants, and transactions from their live services.
5. Operations update the owning service. Transaction and customer changes can trigger cross-service card updates.
6. The dashboard, details pages, alert page, metrics, lists, and charts recompute from the returned API data.

## 5. Authentication and authorization

### Login and manager registration

- `POST /api/auth/register` creates an active manager and returns a JWT session.
- `POST /api/auth/login` authenticates an existing active manager and returns a JWT session.
- `POST /api/auth/refresh` accepts the bearer token and issues a replacement token for an active manager.
- Passwords are verified using Spring Security `PasswordEncoder` (BCrypt).

### Concise authentication responses

| Situation | Response/message |
|---|---|
| Missing username/password | `Username and password are required.` |
| Username does not exist | `No manager with that username exists.` (HTTP 404) |
| Password mismatch | `Incorrect password.` |
| Manager inactive | `This manager account is inactive.` |
| Duplicate username | `A manager with this username already exists.` |
| Duplicate manager phone | `A manager with this phone number already exists.` |
| Invalid registration data | Concise validation message, e.g. 10-digit phone or 8-character password requirement |
| Expired/invalid refresh token | `Your session has expired. Please sign in again.` |

The Angular `CreditApi` deliberately does **not** convert `/api/auth/*` 401/403 responses into generic expiry errors. The login/register dialog displays the API’s concise message. For protected operational API calls, 401/403 clears the session and redirects to `/login?returnUrl=<original route>`.

### Frontend token lifecycle

- Token and user data are held in `localStorage` as `credit-token` and `credit-user`.
- The JWT `exp` claim is parsed to determine expiry.
- Routes except `/login` are protected by `authGuard`.
- A timer refreshes the token approximately one minute before expiry.
- Refresh failure, expired token, logout, or protected-call 401/403 clears local session data.
- After successful login, the user returns to the saved `returnUrl`, otherwise `/` (dashboard).
- Sidebar profile menu displays the signed-in manager, role/Operations, and a working logout action.

> Current boundary: Angular protects UI routes and sends bearer tokens to every API request. Full independent JWT validation inside Customer/Card/Transaction/Merchant services should be added for end-to-end backend enforcement if those services are exposed directly outside this UI.

## 6. Business rules and validation

### Customer rules

- Aadhaar: exactly 12 digits and unique.
- Customer account number: exactly 12 digits and unique.
- Mobile: exactly 10 digits and unique.
- Identity fields cannot be altered through the normal edit form; editable details are name, phone, location, and allowed profile values.
- Created date must never remain null.
- Customer deletion first calls the Card service and requires all associated cards to become `INACTIVE`; deletion is cancelled if deactivation cannot be confirmed.

### Card issue and account rules

- Customer ID and cardholder name are required.
- Card tier and card type are required.
- A customer may hold no more than two **current** cards: one `PRIMARY` and one `ADD_ON`.
- A duplicate primary or duplicate add-on is refused with a concise dialog message.
- Existing paired card means the other type must use the **same tier**.
- Paired cards share card limit, available credit, due date, and expiry date.
- First card receives the tier-derived limit and generated 12-digit unique number; users never type the number.
- Due date must be strictly before expiry date.
- Due date is advanced automatically month-to-month on the original day when repayment succeeds; February is handled safely by the service’s calendar logic.

### Card status and expiration rules

- `ACTIVE`: eligible for card transactions, subject to credit and merchant rules.
- `INACTIVE`: no transactions allowed.
- `BLOCKED`: no transactions allowed.
- Physically expired cards are automatically inactivated when cards are read/processed.
- Expired or replaced cards cannot be reactivated.
- Expiry, due soon/overdue, inactive, blocked, and low available credit are attention conditions.

### Merchant rules

- Merchant MID is unique.
- Merchant account number is unique.
- The frontend generates/validates MID and account-number lengths before submission.
- Only `ACTIVE` merchants are selectable for new card transactions.
- Merchant status can be changed in merchant details.

### Transaction and balance rules

- Only active, non-expired cards may create a card transaction.
- Only active merchants may create a merchant transaction.
- Debit transaction types are `PURCHASE` and `AUTHORIZATION`.
- Debit amount cannot exceed effective available credit.
- A new debit begins as `PENDING` or `AUTHORIZED`; it cannot be created directly settled/failed/cancelled.
- Debit credit is reserved once, tracked by `creditReserved`, to prevent duplicate reservation when status changes.
- `FAILED` or `CANCELLED` debit transactions release any reservation.
- Settled/cancelled transactions cannot be status-changed again.
- A repayment is `PAYMENT`, uses the card/self repayment context, and completes immediately.
- Repayment must be greater than zero and cannot exceed outstanding balance (`limit - available`).
- When available equals limit, repayment is refused because there is no outstanding debt.
- A deleted debit transaction releases its reservation before deletion.
- Repayment increases available credit and advances the shared card account due date.

### Renewal rules

- Renewal is available for a current card in the renewal window (currently 30 days before expiry).
- Renewal is not valid for an already replaced card.
- New expiry/due inputs are validated; due must precede expiry.
- The service issues replacement physical cards for the account pairing, preserves tier and shared balance, and links old/new cards through replacement IDs.
- Old cards remain historic and inactive/replaced; they must not re-enter active transactions or current attention lists.
- Current cards inherit the account’s due/expiry/balance context; alerts and repayments target the current replacement card.

### Merchants

- Search uses merchant name, account number, or category; MID is not required in the user search interface.
- Add merchant opens a dialog rather than route navigation.
- Duplicate MID/account errors are parsed to short dialog messages.
- List supports merchant detail navigation and deletion confirmation.
- Detail supports merchant status/profile edit and shows associated cards/transactions.
- Associated cards include active, inactive, and blocked cards. Card-number, transaction type, status, and date filters are provided.

### Transactions

- Search by card number, transaction ID, or merchant name.
- Independent filters for transaction type, status, and payment method allow combinations such as `PURCHASE` + `PENDING` + `SWIPE`.
- Amount-range control derives min/max from the actual transaction data and uses a two-thumb range presentation.
- New transaction opens a dialog, shows selected card tier/limit/held/effective available, only allows active card/merchant choices, and blocks over-limit debit amounts.
- Delete asks for confirmation. Backend credit release occurs before deletion where needed.
- Detail page shows a more visual summary, India date/time, masked card number with eye toggle to show/hide, card/merchant links, and status settlement actions.
- Repayment detail is explicitly labelled debt/card repayment; merchant context is self rather than an unrelated merchant.

### Needs attention

A card appears when it is current and has any of:

- `BLOCKED` status;
- `INACTIVE` status;
- expired, or expires within 30 days;
- overdue, or due within 14 days;
- low effective available credit (15% or less of limit).

Historic replaced cards are deliberately excluded, so a renewed card account is not continually flagged by the predecessor’s old expiry/due dates.

## 10. Shared balance and transaction safety mechanism

The system uses the following protections to avoid credit being exceeded when multiple pending transactions are later settled:

1. On a debit (`PURCHASE`/`AUTHORIZATION`), available credit is checked before saving.
2. The card service reduces available credit immediately and the transaction is marked `creditReserved=true`.
3. Completing the same transaction does not reserve it again.
4. Failing/cancelling/deleting a debit releases the reservation once.
5. Repayments add available credit back, only up to the current outstanding balance.
6. Primary and add-on cards calculate and display the same account-level effective available balance.

This reservation model makes a group of pending authorizations safe to settle sequentially: their amount has already been held against available credit. The UI additionally calculates `effectiveAvailable` and `heldAmount` from live cards/transactions to present correct availability while services update.

## 11. Error handling conventions

- Backend validation should return a simple JSON object with `message`; no trace should be displayed by dialogs.
- Frontend `CreditApi.messageFrom()` prioritizes `message`, then `error`, then a neutral HTTP failure message.
- Merchant duplicate exceptions are mapped by `ApiExceptionHandler` to an appropriate concise client response.
- Authentication form errors are local to the dialog/form and loading always exits in `finally`.
- Confirmation is used before destructive user actions such as customer, merchant, or transaction deletion.

## 12. Startup and verification

### Start order

1. Start Oracle and Eureka configuration if used by the service environment.
2. Start Customer (`8081`), CreditCards (`8082`), Transactions (`8083`), Merchant (`8084`), and Manager (`8085`).
3. Start Angular from `C:\Project\Frontend\credIT-angular` using the configured Angular serve command.

### Build verification commands

```powershell
# Angular
Set-Location C:\Project\Frontend\credIT-angular
npx.cmd ng build --configuration development

# Each Spring Boot service
Set-Location C:\Project\Manager     # or Customer, CreditCards, Transactions, Merchant
```

### Essential acceptance checks

1. Register a manager; try duplicate username and duplicate phone.
2. Try an unknown manager username and incorrect password; confirm the exact form messages and that the button stops loading.
3. Login, navigate to a protected deep route, expire/logout, then login and confirm return to that route.
4. Register a customer; validate 10-digit phone, 12-digit Aadhaar, 12-digit generated account, and UTC created date.
5. Issue primary and add-on cards; prove duplicate type and third-card prevention.
6. Create a transaction within available credit; attempt a debit over availability; test inactive/blocked/expired card and inactive merchant rejection.
7. Complete, cancel, delete, and repay transactions; verify availability and due date update once.
8. Renew a near-expiry card; verify historic card stays inactive and replacement becomes current in alerts/balance/repayment views.
9. Delete a customer and verify associated cards are inactivated before deletion.
10. Check every table/list with more than ten records and page through results.
